# Mobile UI and iOS notifications QA — 27 October 2026

## What changed

- Notifications render as a native modal dialog portalled to `document.body`, outside the discussion header and its clipping/stacking contexts. Native focus trapping, Escape, an explicit close button and backdrop dismissal replace the fragile blur/outside-pointer interaction.
- Custom select menus are portalled outside layout containment, or into the active native dialog when one owns the trigger. Sorting and sender filters remain above their surfaces.
- Mobile discussion header controls are 44 × 44 CSS pixels, including at 320 px. Safe-area insets protect the header, composer, side panel and dialogs. Inputs use at least 16 px text to avoid automatic iPhone field zoom; user pinch zoom remains enabled.
- VisualViewport resize/scroll updates bound the chat and dialogs to the visible area above the software keyboard. Small dialogs scroll; form and chapter-dialog close controls remain at the top while scrolling.
- The installed app has a stable manifest ID/scope, Apple touch icon and Apple web-app metadata.
- iPhone/iPad browser tabs show installation instructions instead of a misleading or unusable push-enable action. Installed iOS apps and supported Android browsers can request permission directly from the enable button. Unsupported/denied/device-check failure states do not prevent reading the in-app inbox.
- Every delivered service-worker push now produces a visible notification. The former visible-comment suppression could violate Safari's no-silent-push requirement. If the active account changed, the worker shows only generic content and clicking goes to the homepage; no previous account's message is exposed.
- Apple push endpoint validation accepts Apple-controlled `*.push.apple.com` hosts while rejecting lookalikes. Service-worker registration bypasses cached scripts and `/sw.js` explicitly revalidates so the fixed worker can replace existing installations.

## Browser QA scope

The available browser is desktop Chrome/Blink. The real React components and all lesson content were exercised in an isolated iframe fixture; API, account, service-worker, permission and iOS-install conditions were mocked. This is responsive-layout and interaction QA, not a claim of native Safari/WebKit, physical Android hardware, real touch/IME behavior, or APNs/FCM delivery testing.
